# ASSUMPTIONS THIS FILE MAKES:
#   1. Login is interactive. The first two lines below are the username and
#      password for the pre-existing hsams admin account.
#   2. The equipment / rental_agreements / maintenance_logs collections are
#      EMPTY before this run. Equipment is selected by numbered list
#      position, and those numbers assume equipment is inserted in the exact
#      order added in this file (1=Drill, 2=Excavator, 3=Tent, 4=Saw).
#   3. Reports is now fully implemented, so it's tested here rather than
#      skipped.
#   4. "Change password" (Settings option 1) is still skipped — not because
#      it's risky anymore, just wasn't asked for. Say the word if you want
#      it added in.
#   5. Rental due dates are kept within about a year of each other, not
#      spanning multiple years, since totalCost is derived from the day
#      span and multi-year spans were producing unrealistically large costs.
#   6. Check-in return dates are fixed calendar dates chosen a few weeks
#      out from whenever this file was generated, since checkoutDate is
#      whatever LocalDate.now() is at the moment you actually run this, and
#      returnDate must be >= checkoutDate or checkInEquipment() rejects it.
#      This assumes you run this file within roughly a month or so of
#      generation — if you wait much longer, push these dates forward
#      before running, or the Excavator check-ins may get rejected.
#   7. This run exercises both a normal/early return AND a late return on
#      the Excavator (checked out and returned twice), to give the new
#      Reports functionality richer, more realistic data than a single
#      cost datapoint would.
#   8. This run also exercises the checkOutEquipment() status-guard fix and
#      the editEquipmentDetails() "mark as available" recovery fix
#      together: logging maintenance on the Excavator flips it to
#      IN_MAINTENANCE -> an attempted checkout is rejected -> editing it
#      and answering Y to the recovery prompt flips it back to AVAILABLE.
#   9. Dates for the Drill's OVERDUE_RETURN, WARRANTY_EXPIRING, and
#      MAINTENANCE_DUE alerts are chosen safely in the past so those alerts
#      fire regardless of the exact day this is run.
