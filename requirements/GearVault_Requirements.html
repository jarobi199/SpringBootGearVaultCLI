01 / Overview
Project Overview

Application Summary

GearVault is a menu-driven command-line application built with Java, Spring Boot, and MongoDB. It manages an equipment and tool rental business — cataloging every item in inventory, tracking who has it out and when it's due back, logging maintenance work, and computing utilization and revenue on demand. The rental operator checks equipment out to a customer, records the return, and the system flags overdue rentals, equipment due for service, and warranties about to lapse.

The architecture follows the same four-collection pattern established across the CLI series: users, equipment, rental agreements, and maintenance logs are all separate top-level documents. Rental agreements reference their equipment by equipmentId. Maintenance logs reference their equipment the same way, enabling cross-equipment aggregation without loading equipment documents. Rental rate strategies provide the core OOP design surface, with each equipment subtype pricing a rental differently based on how that category is actually rented in the field.

Technology Stack

Spring Boot Entry point via CommandLineRunner. No web layer. Spring DI wires all services. SessionContext holds the current logged-in user.
Spring Data MongoDB Four repositories: UserRepository, EquipmentRepository, RentalAgreementRepository, and MaintenanceLogRepository. Rental agreements reference equipment by equipmentId. Polymorphic _class discriminator for equipment subtypes in the equipment collection.
Java OOP Abstract Equipment with three concrete subtypes each implementing computeRentalCost() differently. Strategy pattern for rental pricing — each subtype instantiates its own RentalRateStrategy in the no-arg constructor; field is @Transient. Factory pattern for equipment creation. Chain of responsibility for alerts.
Menu System Two-level numbered menus. IMenu interface with show() and printOptions() — all menu classes implement it directly. Scanner-based InputHandler with debug mode reading from test_input.txt. do-while loop navigation. 0 always means Back or Exit.
BCrypt Passwords hashed via Spring Security Crypto.

Rental Rate Strategies

Rate fields live on the subtype that actually needs them — hourlyRate/dailyRate on PowerTool, dailyRate/depositAmount on HeavyMachinery, flatEventRate on EventEquipment — since they aren't shared across categories the way purchasePrice is. Because of that, RentalRateStrategy<T extends Equipment> is generic and each strategy is handed the whole subtype-specific object rather than a single generic rate: double computeCost(T equipment, int days). Each equipment subtype initializes its own strategy in the no-arg constructor (e.g. this.rateStrategy = new HourlyCappedRateStrategy()) and declares the field typed to itself, e.g. RentalRateStrategy<PowerTool> rateStrategy on PowerTool. Since MongoDB deserializes via the no-arg constructor, the strategy is always wired whether the object is freshly created by EquipmentFactory or loaded from the database — no post-load wiring needed. The field is annotated @Transient so it is never persisted. computeRentalCost(int days) on each subtype delegates to rateStrategy.computeCost(this, days), passing itself so the strategy can read its own rate fields directly.

SubtypeStrategyFormulaExample
PowerTool HourlyCappedRateStrategy min(equipment.hourlyRate × 8, equipment.dailyRate) × days, with a 1-day minimum $8/hr drill, $35/day cap, rented 3 days = min(64, 35) × 3 = $105
HeavyMachinery TieredDailyRateStrategy equipment.dailyRate (day 1) + (days − 1) × 0.80 × equipment.dailyRate + equipment.depositAmount $220/day excavator, 4 days = $220 + (3 × $176) = $748 + deposit
EventEquipment FlatEventRateStrategy equipment.flatEventRate × equipment.quantityAvailable $20/bundle rate × 8 bundles available = $160

Alert Strategies

OverdueReturnStrategy supports() — true for any non-null Equipment currently referenced by an ACTIVE rental agreement. evaluate() — fires when today's date is past the agreement's dueDate plus the current user's overdueGraceDays; returns an AlertResult with AlertType.OVERDUE_RETURN, the equipment, and a message showing days overdue. Requires RentalAgreementService to look up the active agreement. Only invoked from AlertMenu.
MaintenanceDueStrategy supports() — true for any non-null equipment. evaluate() — fires when no maintenance log exists and the equipment is more than 6 months old, or when the most recent service is more than 6 months old (or, for HeavyMachinery, when engineHours exceeds the hoursAtService value from that equipment's most recent MaintenanceLog by more than 250 hours — there is no separately stored threshold field); returns an AlertResult with AlertType.MAINTENANCE_DUE and a message indicating last service date or "never serviced." Requires MaintenanceLogService. Only invoked from AlertMenu.
WarrantyExpiringStrategy supports() — true for any equipment with a non-null warrantyExpiry. evaluate() — fires when the warranty expiry date is within 30 days of today; returns an AlertResult with AlertType.WARRANTY_EXPIRING and a message showing the expiry date. Only invoked from AlertMenu.

Key Design Notes

Four Collections Users, equipment, rental agreements, and maintenance logs are all separate top-level documents. Rental agreements and maintenance logs both reference their item by equipmentId rather than embedding — this keeps the equipment document small and allows either collection to be queried independently (e.g. all active rentals, or all maintenance history) without loading equipment.
Rental Rate Strategy Rate fields (hourlyRate, dailyRate, depositAmount, flatEventRate) live directly on the subtype that charges them, not on the abstract Equipment class, since they aren't shared across categories. RentalRateStrategy<T extends Equipment> is generic so each strategy receives the whole subtype-specific object and reads its own fields directly, rather than the interface trying to guess which single "base rate" to pass. Each subtype initializes its own strategy in the no-arg constructor. MongoDB deserializes via the no-arg constructor, so the strategy is always set on load without any post-load hook. The field is @Transient and never stored. computeRentalCost(int days) on each subtype delegates to rateStrategy.computeCost(this, days).
EquipmentFactory EquipmentFactory.create(EquipmentType) prompts common fields first (name, brand, model, serial number, purchase price, purchase date, condition, optional warranty expiry and notes), then type-specific fields, including the rate fields each subtype's strategy needs. Power tools prompt for voltage, battery flag, tool class, hourly rate, and daily rate cap. Heavy machinery prompts for engine hours, cert requirement, fuel type, daily rate, and deposit amount. Event equipment prompts for category, quantity available, setup-required flag, and flat event rate.
BookingNote Selection When viewing or editing setup notes on EventEquipment, records are listed by numbered ArrayList index. The user selects by number — no UUID needed. The list is stable for the duration of the menu interaction.
Status & Checkout An equipment item's status is set to RENTED when a rental agreement is created and reverts to AVAILABLE when the agreement's return is recorded. Attempting to check out an item that is not AVAILABLE is rejected with a clear message pointing to its current status.
MaintenanceLog Full top-level documents in their own collection, same pattern as MaintenanceRecord in the Auto Warehouse project. This allows cross-equipment maintenance reports (total spend, cost by service type) without loading every equipment document. MaintenanceLogRepository exposes findByEquipmentId() and findByUserIdOrderByServiceDateDesc().
Equipment Snapshot RentalAgreement and MaintenanceLog both copy equipmentName, equipmentSerialNumber, equipmentBrand, and equipmentModel at creation time, straight from the Equipment object already in hand — no extra query. This is a point-in-time snapshot, not a cache: the point is that a rental or service record should always read as it did at that moment, the same way a receipt still shows the product name and price as they were at checkout even after the store re-labels or discontinues the item. These fields are never re-synced if the source equipment is later renamed. equipmentId is kept alongside the snapshot for anything that needs the equipment's current state — status, condition, alert evaluation — rather than its identity at that point in time.

07 / Alerts
Alert System — Chain of Responsibility

All alert strategies are registered in a central AlertManager as a Spring-managed List<AlertStrategy>. AlertMenu calls alertManager.evaluate(equipment) passing a List<Equipment> — the manager iterates every item against every strategy, each deciding via supports() whether it applies. Each strategy returns an AlertResult carrying the triggering Equipment, an AlertType enum value (with a displayName field), and a human-readable message. Adding a new alert type requires zero changes to any service class — implement AlertStrategy, annotate with @Component, and Spring auto-registers it.

AlertStrategy.java  ·  AlertResult.java  ·  AlertType.java  ·  AlertManager.java

Alert System — Chain of Responsibility
Java
// AlertStrategy.java — single interface for all alert strategies
public interface AlertStrategy {
    boolean supports(Equipment equipment);
    AlertResult evaluate(Equipment equipment);
}

// AlertType.java — enum with displayName for rendering in AlertMenu
public enum AlertType {
    OVERDUE_RETURN("Overdue Return"),
    MAINTENANCE_DUE("Maintenance Due"),
    WARRANTY_EXPIRING("Warranty Expiring");

    private final String displayName;
    AlertType(String displayName) { this.displayName = displayName; }
    public String getDisplayName() { return displayName; }
}

// AlertResult.java — structured result carrying equipment, type, and message
public class AlertResult {
    private final Equipment equipment;
    private final AlertType   alertType;
    private final String      message;
    // constructor + getters...
}

// AlertManager.java — Spring collects ALL AlertStrategy beans automatically
@Component
public class AlertManager {
    private final List<AlertStrategy> strategies;
    public AlertManager(List<AlertStrategy> strategies) {
        this.strategies = strategies;
    }
    public List<AlertResult> evaluate(List<Equipment> equipment) {
        return equipment.stream()
            .flatMap(e -> strategies.stream()
                .filter(s -> s.supports(e))
                .map(s -> s.evaluate(e)))
            .collect(Collectors.toList());
    }
}

// In AlertMenu — "View all alerts": fetch all equipment, evaluate, display
List<Equipment> allEquipment = equipmentService.findByUserId(userId);
List<AlertResult> results = alertManager.evaluate(allEquipment);
results.forEach(r -> System.out.printf(
    "[%s] %s %s — %s%n", r.getAlertType().getDisplayName(),
    r.getEquipment().getBrand(), r.getEquipment().getName(), r.getMessage()));

// In AlertMenu — "Overdue return alerts": filter to type only
results.stream()
    .filter(r -> r.getAlertType() == AlertType.OVERDUE_RETURN)
    .forEach(r -> System.out.println(r.getMessage()));
08 / Navigation
Menu Navigation Pattern

Every menu class implements the IMenu interface, which declares show() and printOptions(). The body of show() is a do-while loop: print options → read integer → switch dispatch → exit on 0. Returning from show() pops back to the caller automatically — no explicit stack needed. Spring injects all services; menu classes own only I/O logic.

Menu Navigation Pattern
Java
// IMenu.java — implemented by all menu classes
public interface IMenu {
    void show();
    void printOptions();
}

// RentalMenu.java — typical menu implementation
@Component
public class RentalMenu implements IMenu {

    private final RentalAgreementService rentalService;

    public RentalMenu(RentalAgreementService rentalService) {
        this.rentalService = rentalService;
    }

    @Override
    public void printOptions() {
        System.out.println("1. Check out equipment");
        System.out.println("2. Check in / return");
        System.out.println("3. View active rentals");
        System.out.println("4. View overdue rentals");
        System.out.println("5. View rental history");
        System.out.println("0. Back");
    }

    @Override
    public void show() {
        int choice;
        do {
            printOptions();
            choice = InputHandler.readInt();  // static — no injection needed
            switch (choice) {
                case 1 -> checkOutEquipment();
                case 2 -> checkInEquipment();
                case 3 -> viewActiveRentals();
                case 4 -> viewOverdueRentals();
                case 5 -> viewRentalHistory();
            }
        } while (choice != 0);
    }   // returning here pops back to MainMenu automatically
}
